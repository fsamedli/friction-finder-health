# Friction Finder v0.6 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Turn the prototype into a detect → explain → act → prove loop for one site, served by
FastAPI with a React front end. The v0.5 "Ask" flow is kept as the drill-down.

**Architecture:**
- New synthetic tables are generated by a separate module with its own RNG, so v0.5 data stays
  byte-identical.
- A pure-Python analytics module (`app/impact.py`) computes excess cost, the engagement–KPI
  linkage, and difference-in-differences.
- FastAPI (`api/main.py`) exposes typed endpoints. These double as the tool set for a later
  tool-using "Ask" assistant.
- A Vite/React/TS/Tailwind/Recharts app in `web/` is built to `web/dist` and served by FastAPI:
  one process on demo day.

**Tech Stack:**
- Python 3, pandas, numpy, statsmodels, duckdb (existing), FastAPI, uvicorn.
- Node 25 / npm 11, Vite, React 18, TypeScript, Tailwind v3, Recharts, react-router.

**Spec:** `docs/specs/2026-09-23-detect-explain-act-prove-design.md`

## Global Constraints

- **MIN_N = 4.** No survey value for a team-wave with n < 4. Teams with headcount < 4 show no
  team-level ops numbers ("rolled up to site").
- **No model calls** on Board / Why / Plan / Did it work / Business case. Each answers in under 1 s.
- **Existing work stays green.** The existing 32 tests and 12 evals must still pass. Existing
  generated CSVs must not change.
- **Copy rules:**
  - Say "AI-assisted workflow," never "agents."
  - Never say "eliminates hallucinations."
  - Use "points on a 5-point scale," never "percent," for item changes.
  - Label associations "association, not cause."
  - Label the DiD "directional, not causal."
  - Label follow-up data "synthetic."
- **Money:** every dollar figure traces to `unit_costs.json`, and each entry there has a source or
  is marked as an assumption. Late departures carry no default cost.
- **No manager scorecard.** Board rows are teams and obstacles, not people. Manager names are
  never shown on the board.
- **Pattern ids:** the new patterns are **P11, P12, P13**. P9 and P10 already exist in
  `generate.py`, so the spec's "P9/P10" wording maps to P11/P12.
- **Demo clock:** there are two "as of" dates.
  - `2026-09-15`: wave 2 is in. The board window is Jun–Aug.
  - `2026-11-30`: the review date. The Did-it-work post window is Oct–Nov.
  - Plan start is 2026-09-21. Review date is 2026-11-30 (the spec said Nov 20; moved to align
    with monthly data).

## Review Focus

1. **Did it work** opened for a plan whose review date is after the as-of date. Expected: "review
   date not reached, N days to go," and no estimate.
2. **A plan created live** for a team with no follow-up months. Expected: "not enough follow-up
   data," not a crash or a fake number.
3. **Unit cost edited** to blank, 0, negative or text. Expected: 422 for invalid input, 0 allowed,
   and the value per site recomputes.
4. **No API key.** Expected: every page except Ask works; Ask returns the rules-mode brief with a
   visible "rules mode" chip.
5. **A small team** (Maintenance Night, headcount 2) on the board and in `/why`. Expected: no scores
   or ops numbers, the "rolled up to site" label, and HTTP 200.

**Generation rules.** Own RNG, `np.random.default_rng(4242)`.
- Engagement state per team-month:
  - Months ≤ 2026-06 use the team's wave 1 observed grand mean and q02 mean, from `responses`.
  - Later months use wave 2.
  - Missing means fall back to the site-shift mean.
- Rates per head per month, with `g` = grand mean and `q2` = q02 mean:
  - `absence_days ~ Poisson(h * 0.55 * exp(-0.9*(g-3.85)))`
  - `late_departures ~ Poisson(h * 0.60 * exp(-1.1*(q2-3.85)))`
  - `quits ~ Poisson(h * 0.022 * exp(-0.8*(g-3.85)))`
  - `rework ~ Poisson(h * 0.30 * exp(-0.7*(q2-3.85)))`
  - `injuries ~ Poisson(h * 0.00125)`: independent of engagement. This is the planted null, P13.
- **P11, Richmond Night A:** multiply late departures ×1.8, absences ×1.35 and quits ×1.6 for
  2026-06..2026-09. For 2026-10..11 the multipliers are 1.0, but the engagement state stays at
  wave 2: the fix removes the obstacle.
- Comparison teams: the other Night teams with headcount ≥ 4.

```python
AS_OF_DETECT = "2026-09-15"; AS_OF_REVIEW = "2026-11-30"; KPIS = ["absence_days","late_departures","quits","injuries","rework"]
def window(as_of: str, months: int = 3) -> list[str]               # full months before as_of
def board(site_id: int, as_of: str, costs: dict) -> dict          # {"site","as_of","window","total_excess","by_kpi":{k:$},"teams":[TeamRow]}
#   TeamRow = {"team_id","team_name","shift","headcount","status":"red|amber|green|rolled_up",
#              "excess_cost","excess_by_kpi":{k:{"count":float,"dollars":float}},
#              "spark":{k:[{"month","rate"}]},"engagement":{"n_w1","n_w2","grand_w1","grand_w2","biggest_drop":{"item","label","delta"}}|None}
def why(team_id: int, as_of: str, costs: dict) -> dict            # {"team", "kpi_trend":[{"month",k...,"baseline_"+k...}], "item_changes":[{"item","label","w1","w2","delta"}], "links":[Link], "suppressed":bool}
def quartile_link(kpi: str, item: str = "grand") -> dict          # {"kpi","item","top_q_rate","bottom_q_rate","pct_diff","n_cells","n_per_quartile"}
def association(kpi: str, item: str = "grand") -> dict            # {"kpi","item","slope","ci_low","ci_high","p","n_cells","n_teams","verdict":"association|no association detected"}
def load_plans() -> list[dict]; def save_plan(plan: dict) -> dict # plans.jsonl + seed
#   Plan = {"id","team_id","item","focus","actions":[{"text","owner","due"}],"start","review","kpi","status":"approved|draft|rejected","note"}
def did(plan: dict, as_of: str, costs: dict) -> dict              # {"status":"ok|not_reached|insufficient","days_to_go"?, "estimate","ci_low","ci_high","treated":{"pre","post"},"comparison":{"pre","post","teams":[...]},"placebo":[{"team","estimate"}],"dollars_per_quarter","verdict":"worked|inconclusive|no effect"}
def value_case(costs: dict, headcount: int = 300) -> dict         # per-site annual value range; every input with source
```

**Method notes. Put these in docstrings; they are also the Q&A answers.**
- `excess`: team rate per head-month minus the median rate of other reportable teams on the same
  shift in the same window, floored at 0, × headcount × months × unit cost.
- `status`:
  - `rolled_up` if headcount < MIN_N.
  - `red` if excess ≥ $5,000 in the window **and** (any item drop ≤ −0.30 with n ≥ 4 in both waves).
  - `amber` if exactly one of those holds.
  - `green` otherwise.
  - Constants: `RED_DOLLARS = 5000`, `ITEM_DROP = -0.30`.
- `quartile_link`: cells are reportable team-waves (n ≥ 4 in that wave). The KPI rate is taken
  over the quarter the wave closed in (wave 1 → 2026-01..03, wave 2 → 2026-07..09). Cells are
  split into quartiles by item mean; `pct_diff` = (bottom − top) / bottom × 100. This is the same
  presentation as Gallup's meta-analysis.
- `association`: statsmodels OLS of `rate ~ item_mean` over the same cells, with standard errors
  clustered by team (the same team appears twice). The verdict is "association" if the 95% CI
  excludes 0.
- `did`:
  - Pre window: the 3 full months before `plan.start`. Post window: full months from the month
    after start through `min(review, as_of)`.
  - Comparison: other Night teams (same shift as the treated team) with headcount ≥ MIN_N.
  - Estimate = (T_post − T_pre) − (C_post − C_pre), on rates per head-month.
  - SE comes from Poisson variance: var(rate) = count / exposure². Pooled for the comparison.
    CI = ± 1.96 SE.
  - Placebo: the same estimate for each comparison team treated as if it had acted.
  - Verdict "worked" if the CI is entirely on the helpful side (below 0 for these KPIs).
  - Dollars use the plan KPI's unit cost if it is > 0; otherwise the count avoided per quarter.
